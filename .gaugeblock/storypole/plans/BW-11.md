# GB-59: Update Benchwork for Multi-Repository Workspace Rollups and Store Routing

> **Status:** Ready  
> **Target Scope:** `benchwork` (`benchwork-core`, `benchwork-cli`, `benchwork-mcp`)  
> **Key Invariants:**  
> 1. Hard 250 LOC rule on all `.rs` files.  
> 2. Zero-panic safety: no `.unwrap()` / `.expect()` in production library paths (`thiserror`).  
> 3. Standalone & Multi-Repo Transparency: running `benchwork up` inside a standalone repo clone (`benchwork/`) or in the meta-harness (`neurosymbolic-suite`) must work seamlessly out of the box.  
> 4. Non-breaking Wire Contracts: TypeScript UI models and WebSocket payloads remain backward-compatible.  

---

## 1. Executive Summary & Problem Statement

With `GB-57` and `GB-58` having delivered multi-repository workspace discovery, unified SQLite aggregation, and distributed task ledgers to `storypole`, `benchwork` requires updates to consume these capabilities:

1. **Panel 2 (Live DAG Board & Backlog):**
   * Currently, `benchwork-core::dag_service::get_dag_view` calls `StorypoleStore::open(root_path)`. When running in the meta-harness workspace, it only queries the root store (`GB-*` meta-tasks).
   * It must adopt `StorypoleWorkspaceStore::open(root_path)`, which rolls up tasks across all member repositories (`benchwork`, `miter`, `sawhorse`, `outfeed`, etc.) while respecting `--repo` filters.
2. **Task Mutations & Lifecycle Routing:**
   * Handlers for Claim, Heartbeat, Handoff, Update, Link, and Archive currently open `StorypoleStore::open(root_path)`.
   * For distributed tickets belonging to member repositories (e.g. `BW-*`, `MTR-*`, `OF-*`), the root store cannot find them. Benchwork must route mutations via `ws.resolve_governing_store_name(key)` to the governing member store (`ws.member_store_mut(repo)`).
3. **AI Chat Studio Context Injection (`context_injector.rs`):**
   * Currently hardcodes `.gaugeblock/storypole/ledger.jsonl` and `.gaugeblock/storypole/plans/{key}.md`.
   * In a standalone clone of `benchwork` (or other sub-repos), these files live under `.storypole/`. Context injection must resolve both `.storypole/` and `.gaugeblock/storypole/` paths.
4. **Capabilities Scanner (`capabilities.rs`):**
   * Currently checks `root_path.join(".storypole/config.toml")` specifically. Must use `StorypoleStore::open` / `StorypoleWorkspaceStore::open` to accurately detect active Storypole stores and compute task counts.

## 3. Execution Plan & Verification Gates

### Step 1: Adopt `StorypoleWorkspaceStore` in `dag_service.rs`
* Update `get_dag_view` to open `StorypoleWorkspaceStore::open(root_path)` with fallback to `StorypoleStore::open(root_path)`.
* Update mutation services (`update_task_details`, `claim_task_lease`, `handoff_task_checkpoint`, `archive_task_service`, `link_tasks_service`) to route to the governing member store via `ws.resolve_governing_store_name`.
* *Verification Gate:* `cargo test -p benchwork-core --test dag_service_tests`

### Step 2: Make `context_injector.rs` Standalone & Workspace Aware
* Replace hardcoded `.gaugeblock/storypole` paths with `StorypoleStore::resolve_dot_dir(root_dir)`.
* Search both root plans and member plans when resolving `@task:KEY`.
* *Verification Gate:* `cargo test -p benchwork-core --lib chat_harness::tests`

### Step 3: Modernize `capabilities.rs` Storypole Scanner
* Update `scan_storypole` to use `StorypoleStore::find_enclosing_store` or `StorypoleWorkspaceStore::open` to illuminate `caps.storypole_active` and aggregate metrics.
* *Verification Gate:* `cargo test -p benchwork-core --test integration_tests`

### Step 4: Full Benchwork Workspace Verification
* Run Tier 2 verification gate across `benchwork`:
  `cargo fmt --check -p benchwork-core -p benchwork-cli`
  `cargo clippy -p benchwork-core -p benchwork-cli --all-targets -- -D warnings`
  `cargo test -p benchwork-core -p benchwork-cli`
* Verify `benchwork up` surfaces tasks from both the workspace root and member repositories.
